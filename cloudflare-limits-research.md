# Cloudflare limits research

Sources reviewed on 2026-08-22:

- https://developers.cloudflare.com/workers/platform/limits/
- https://developers.cloudflare.com/workers/platform/pricing/

The official Workers limits page currently shows, for Workers Free versus Workers Paid: 100,000 requests per day versus no request limit; 10 ms versus 5 minutes of CPU time per invocation; 128 MB memory on both; 50 versus 10,000 subrequests per request; 6 simultaneous outgoing connections per request on both; 64 versus 128 environment variables per Worker; 5 KB versus 5 KB per environment variable; 3 MB versus 10 MB Worker size; 1 second startup time on both; 100 versus 500 Workers per account; 20,000 versus 100,000 static asset files per Worker version; and 25 MB maximum individual static asset size on both. The current Nuelifi production bundle is roughly 0.49 MB total across four static files, so it is far below the static-asset file and size limits. The AI provider calls are outbound subrequests and should remain bounded and infrequent; they are not generated by static asset requests.

The official pricing page states that Workers Free includes 100,000 requests per day. The Standard paid model includes 10 million requests per month plus additional requests billed at $0.30 per million, with 30 million CPU milliseconds included per month plus $0.02 per additional million CPU milliseconds. Static-asset requests are treated separately from Worker execution in the pricing documentation; the current app’s static bundle is small and the dynamic AI endpoint is the main usage/cost concern.

Implementation consequence: retain the compact Vite bundle and static-asset deployment, do not add large local media, keep AI requests behind authenticated `/api/analyze`, bound upstream provider timeouts, and plan an application-level daily analysis quota before opening the service broadly. No hosting-plan upgrade or Cloudflare limits change is required for the current prototype scale.

## Future Pro-plan payment architecture

Sources reviewed:

- https://docs.stripe.com/billing/quickstart
- https://docs.stripe.com/webhooks

Stripe’s official subscription quickstart describes a server-created Checkout Session in subscription mode, with price and line-item details kept server-side, followed by Stripe-hosted Checkout and success/cancel redirects. Stripe’s webhook guidance requires a public HTTPS POST endpoint, verification of the raw request signature with the webhook secret, fast 2xx acknowledgement, and asynchronous handling of subscription lifecycle events.

Recommended future Nuelifi design: add an authenticated Worker endpoint that creates a Checkout Session from a server-held Stripe Price ID; redirect the user to Stripe-hosted Checkout; handle verified `checkout.session.completed`, subscription update, cancellation, and invoice/payment failure events in a webhook endpoint; then update `subscriptions.plan`, `subscriptions.status`, `provider_customer_id`, and `provider_subscription_id` in Supabase using a service-role server-side connection. The frontend should read entitlements from the server/database, not from client state. Add a Stripe customer-portal endpoint for billing management. Do not put Stripe secret keys, webhook secrets, or price authority in the Vite bundle.

This iteration intentionally leaves payment collection disabled and labels the Profile Pro card as a preview. Ads should be added later only after consent/privacy review, an ad provider is selected, and the application-level AI usage budget is in place.

## Desktop blank-dashboard regression — 2026-08-22

The live wide-layout reproduction showed that the React dashboard content was present in the DOM and had visible computed styles, but `.bottom-nav` had `position: absolute`, `width: 100%`, `height: 100%` of the app shell, and `z-index: 5`. At the desktop breakpoint the app shell is a two-column CSS grid and the navigation is intended to be a grid item in the first column; the absolute positioning removed it from normal grid layout and made the opaque navigation rail cover the entire shell, hiding the main content. The fix is to make the desktop navigation position static so it participates in the grid while retaining the mobile fixed navigation behavior. The rebuilt local preview showed the dashboard content and recent-meal card visibly rendered beside the rail. Computed geometry changed from a full-shell absolute overlay to a static 243px rail at x=1 and a visible 1020px main column at x=244. The production bundle now serves `index-yuNrgsrb.css`, the corrected asset hash, and the same geometry was confirmed at the live Worker URL in preview mode.
